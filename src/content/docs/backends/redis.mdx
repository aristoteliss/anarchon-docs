Redis is the default backend. `RedisBackend` works with Redis 5 or newer, and `ValkeyBackend` with Valkey. In .NET, `RedisBackend` from the `Anarchon.Redis` package serves both, on StackExchange.Redis.

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
import { RedisBackend, Scheduler, ValkeyBackend } from 'anarchon';

new Scheduler({ backend: new RedisBackend({ redis: 'redis://localhost:6379' }) });
new Scheduler({ backend: new RedisBackend({ redis: 'redis://cache.internal:6379' }) });
new Scheduler({ backend: new ValkeyBackend({ valkey: { host: 'localhost', port: 6390 } }) });
```

</TabItem>
<TabItem label=".NET">

```csharp
using Anarchon;
using Anarchon.Redis;

new Scheduler(new SchedulerOptions { Backend = new RedisBackend("localhost:6379") });
new Scheduler(new SchedulerOptions { Backend = new RedisBackend("cache.internal:6379") });
new Scheduler(new SchedulerOptions { Backend = new RedisBackend("localhost:6390") }); // Valkey
```

</TabItem>
</Tabs>

`ValkeyBackend` is a `RedisBackend` that accepts only the strategies Valkey supports, so `strategy: 'idmp'` is a type error instead of an error from `start()`. Its connection option is `valkey` instead of `redis`, and it has no `idmp` settings. Everything else on this page applies to both. In .NET there is one `RedisBackend` for both servers; `RedisStrategy.Idmp` on Valkey fails at `StartAsync()`.

## Connecting

`redis` accepts a URL, an options object, or a client. In .NET, `Configuration` takes a StackExchange.Redis configuration string, and `Connection` your own multiplexer.

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
new Scheduler({ backend: new RedisBackend({ redis: process.env.REDIS_URL }) }); // rediss:// for TLS; user, password and database go in the URL
new Scheduler({ backend: new RedisBackend({ redis: { host: 'cache', port: 6379, password: process.env.REDIS_PASSWORD, db: 1 } }) });
```

</TabItem>
<TabItem label=".NET">

```csharp
// ssl=true for TLS; user and password go in the configuration string
new RedisBackend(new RedisBackendOptions { Configuration = builder.Configuration.GetConnectionString("redis") });
new RedisBackend(new RedisBackendOptions { Configuration = "cache:6379,password=...,ssl=true", Database = 1 });
```

</TabItem>
</Tabs>

When you pass a URL or options, anarchon opens the connection with `redis` (node-redis) and closes it on `stop()`. In .NET, a `Configuration` makes the backend open a `ConnectionMultiplexer` and close it on `StopAsync()`.

### Your own client

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
import { Redis } from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);
const scheduler = new Scheduler({ backend: new RedisBackend({ redis }) }); // stop() leaves it open
```

</TabItem>
<TabItem label=".NET">

```csharp
var redis = await ConnectionMultiplexer.ConnectAsync(builder.Configuration.GetConnectionString("redis")!);
var scheduler = new Scheduler(new SchedulerOptions { Backend = new RedisBackend(new RedisBackendOptions { Connection = redis }) }); // StopAsync() leaves it open
```

</TabItem>
</Tabs>

These clients are recognized: **ioredis**, **iovalkey**, **node-redis** (`redis`) and **Valkey GLIDE**. Anything else works if it has a `send(command, args)` method that returns the reply. In .NET, any `IConnectionMultiplexer` works, so the one your app registers for caching can be shared.

## Options

<Tabs syncKey="language">
<TabItem label="Node.js">

Options of `new RedisBackend()`. `new ValkeyBackend()` takes the same ones, with `valkey` in place of `redis` and no `'idmp'` strategy:

| Option | Default | Meaning |
| --- | --- | --- |
| `redis` | `localhost:6379` | Connection or client |
| `strategy` | `'lease'` | How one winner is picked: a name, or `{ name, ...settings }` (below) |
| `prefix` | `'cron:'` | Prefix of every key |

A strategy's settings go inside it, so an option that one strategy doesn't use can't be set by mistake: `{ name: 'lease', windowMs: 1 }` is a type error, and an error when the backend is created.

```ts
import { RedisBackend, Scheduler } from 'anarchon';

const backend = new RedisBackend({
  redis: process.env.REDIS_URL,
  strategy: { name: 'script', windowMs: 10 * 60_000 },
  prefix: 'billing:cron:',
});
new Scheduler({ backend });
```

</TabItem>
<TabItem label=".NET">

Properties of `RedisBackendOptions`:

| Option | Default | Meaning |
| --- | --- | --- |
| `Configuration` | `localhost:6379` | A StackExchange.Redis configuration string |
| `Connection` | none | Your `IConnectionMultiplexer`, instead of `Configuration` |
| `Database` | `-1` | The database number; `-1` is the connection's default |
| `Strategy` | `RedisStrategy.Lease` | How one winner is picked (below) |
| `Prefix` | `"cron:"` | Prefix of every key |
| `ScriptWindow` | 5 minutes | `Script` only |
| `IdmpDuration`, `IdmpMaxSize` | 5 minutes, `1000` | `Idmp` only |

A strategy setting given to another strategy, such as `ScriptWindow` with `Lease`, throws an `ArgumentException` when the backend is created.

```csharp
using Anarchon;
using Anarchon.Redis;

var backend = new RedisBackend(new RedisBackendOptions
{
    Configuration = builder.Configuration.GetConnectionString("redis"),
    Strategy = RedisStrategy.Script,
    ScriptWindow = TimeSpan.FromMinutes(10),
    Prefix = "billing:cron:",
});
new Scheduler(new SchedulerOptions { Backend = backend });
```

</TabItem>
</Tabs>

Only `lease` gives the scheduler leases. With the other strategies, the lease options (`overlap`, `maxAttempts` and `catchUpMs` on jobs, `leaseMs` and `heartbeatMs` on the scheduler) aren't offered by the types and are refused if set (in .NET, `Overlap`, `MaxAttempts`, `CatchUp`, `Lease` and `Heartbeat` throw an `AnarchonException` with code `Unsupported`): see [Brokers and leases](../brokers-and-leases/).

## Strategies

A strategy is the command that lets exactly one instance win. Redis executes commands and Lua scripts one at a time, so any single command or script that both checks "is this run taken?" and takes it is atomic.

| Strategy | .NET | Leases | Works on | Remembers a run for |
| --- | --- | --- | --- | --- |
| `lease` (default) | `RedisStrategy.Lease` | **yes** | Redis 5+, Valkey | as long as a late claim could ask for it |
| `stream-id` | `RedisStrategy.StreamId` | no | Redis 5+, Valkey | forever |
| `idmp` | `RedisStrategy.Idmp` | no | Redis 8.6+ only | `strategy.durationSec`, `IdmpDuration` (5 min) |
| `script` | `RedisStrategy.Script` | no | Redis 5+, Valkey | `strategy.windowMs`, `ScriptWindow` (5 min) |

**Use `lease` unless you have a reason not to.** It is the only strategy with backups, overlap protection, retries and catch-up. The others only decide who runs each time; they are kept for minimal setups and for comparison.

### `lease`

One Lua script reads the run's state and decides:

```mermaid
flowchart TD
  claim["claim(job, slot, token)"] --> has{"state for this run?"}
  has -- "none" --> overlap{"an older run of the job<br/>with a live lease?"}
  overlap -- "yes" --> ovl["answer: overlap"]
  overlap -- "no" --> won1["store attempt 1, token, lease end<br/>answer: won"]
  has -- "finished" --> done["answer: done"]
  has -- "running" --> alive{"lease end in the future?"}
  alive -- "yes" --> running["answer: running<br/>(the caller becomes a backup)"]
  alive -- "no" --> attempts{"attempts left?"}
  attempts -- "yes" --> won2["store attempt + 1, the caller's token, a new lease<br/>answer: won"]
  attempts -- "no" --> giveup["mark interrupted<br/>answer: done"]
```

While the job runs, the winner sends a heartbeat that pushes the lease end forward, and at the end it marks the run finished. Both only work with the token of the current attempt.

[Leases](../../internals/leases/) covers the whole mechanism.

### `stream-id`

Each instance adds an entry to the job's stream with the run time as the entry ID. Redis refuses an ID that is not greater than the stream's last one, so only the first `XADD` succeeds.

```
A: XADD cron:sync:runs 1791633610000-0 slot ... token a1  ->  "1791633610000-0"    A runs it
B: XADD cron:sync:runs 1791633610000-0 slot ... token b7  ->  ERR The ID specified in XADD is equal
                                                              or smaller than the target stream top item
```

It is the simplest strategy and remembers runs forever, because IDs only grow.

### `idmp`

Redis 8.6 added idempotent `XADD`. Redis keeps the first entry for an idempotency key and answers repeats with that entry's ID.

```
A: XADD cron:sync:runs IDMP sync 1791633610000 * slot ... token a1  ->  "1791633610012-0"  (stored)
B: XADD cron:sync:runs IDMP sync 1791633610000 * slot ... token b7  ->  "1791633610012-0"  (A's entry)
```

Each instance then reads that entry and compares tokens. With `ValkeyBackend`, `strategy: 'idmp'` doesn't compile. With `RedisBackend` on Valkey or an older Redis, `start()` (`StartAsync()` in .NET) fails with a message that points to the other strategies.

| Setting of `{ name: 'idmp' }` | .NET | Default | Meaning |
| --- | --- | --- | --- |
| `durationSec` | `IdmpDuration` | `300` (5 minutes) | How long Redis remembers a run's ID (1 second to 1 day) |
| `maxSize` | `IdmpMaxSize` | `1000` | How many run IDs Redis keeps per job (1 to 10000) |

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
new RedisBackend({ strategy: { name: 'idmp', durationSec: 900, maxSize: 5_000 } });
```

</TabItem>
<TabItem label=".NET">

```csharp
new RedisBackend(new RedisBackendOptions { Strategy = RedisStrategy.Idmp, IdmpDuration = TimeSpan.FromMinutes(15), IdmpMaxSize = 5_000 });
```

</TabItem>
</Tabs>

### `script`

The same behavior as `idmp` for servers that don't have it. A Lua script scans the stream's recent entries for this run time and appends the claim only if it is absent.

| Setting of `{ name: 'script' }` | .NET | Default | Meaning |
| --- | --- | --- | --- |
| `windowMs` | `ScriptWindow` | `300000` (5 minutes) | How long a claimed run is remembered. Must be longer than a job's `jitterMs + maxLateMs` |

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
new ValkeyBackend({ strategy: { name: 'script', windowMs: 10 * 60_000 } });
```

</TabItem>
<TabItem label=".NET">

```csharp
new RedisBackend(new RedisBackendOptions { Configuration = valkey, Strategy = RedisStrategy.Script, ScriptWindow = TimeSpan.FromMinutes(10) });
```

</TabItem>
</Tabs>

## Keys

With the **`lease`** strategy, each job has five keys. They share one hash tag (the part in braces), so Redis Cluster keeps them on the same node and the scripts can touch all of them:

| Key | Type | Holds |
| --- | --- | --- |
| `{cron:<job>}:state` | hash | Per run: attempt, token, status, runner, lease end |
| `{cron:<job>}:active` | set | Runs not finished yet |
| `{cron:<job>}:slots` | sorted set | Every run in the state, to trim the oldest |
| `{cron:<job>}:runs` | stream | One entry per attempt (history) |
| `{cron:<job>}:results` | sorted set | One result per attempt (history) |

With the **claim-only** strategies there are three:

| Key | Type | Holds |
| --- | --- | --- |
| `cron:<job>:runs` | stream | One entry per claimed run |
| `cron:<job>:manual` | stream | One entry per `runNow()` (`RunNowAsync()`) run |
| `cron:<job>:results` | sorted set | One result per run |

`cron:` is the `prefix`. Every strategy also writes one key, `cron:format`: the store format, so a newer anarchon's data is never misread. A backend refuses to start when it finds a format newer than it reads (`ANARCHON_STORE_FORMAT`, `AnarchonErrorCode.StoreFormat` in .NET). The Node.js and .NET backends write the same keys in the same format, so instances of both can share a job.

## The server's clock

Lease ends are computed with Redis's own `TIME`, inside the script. Instances never compare their clocks with each other, so a clock difference between two instances can't make a live lease look expired.

## Redis Cluster and Sentinel

- **Cluster**: with the `lease` strategy all keys of one job share a hash tag, so every script touches one node. Pass a cluster client you created yourself (an ioredis `Cluster` or a GLIDE cluster client). In .NET, StackExchange.Redis finds the cluster from the configuration string by itself. anarchon's own tests run against single servers.
- **Sentinel and replicas**: point anarchon at the primary. Claims are writes.

:::caution[Failover]
Redis replication is asynchronous. If the primary fails right after acknowledging a claim and before replicating it, the promoted replica doesn't know the run was claimed, and another instance may claim it again. This is rare and applies to anything stored in Redis. Keep jobs [safe to run twice](../../guides/writing-handlers/#make-jobs-safe-to-run-twice).
:::

## Memory

History is trimmed to about `historySize` runs per job (default 1000), and to `historyTtlMs` (`HistoryTtl`) if you set it. A run's state is never trimmed while it is still in progress, or while a late claim could still ask for it.
