## Testing a handler

A handler is a function. The most useful tests call it directly with a context you build yourself. No scheduler is involved.

In .NET only the scheduler creates a `JobContext`, so let the handler pass on what it uses (the slot, the attempt, the token) to a method you can call from a test.

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
import { test } from 'node:test';
import assert from 'node:assert/strict';
import type { JobContext } from 'anarchon';
import { buildInvoices } from './invoices';

function context(overrides: Partial<JobContext> = {}): JobContext {
  const slot = Date.UTC(2026, 9, 1, 6); // 2026-10-01T06:00:00Z
  return {
    name: 'monthly-invoices',
    slot,
    scheduledAt: new Date(slot),
    instanceId: 'test',
    manual: false,
    attempt: 1,
    reason: 'scheduled',
    signal: new AbortController().signal,
    ...overrides,
  };
}

test('running twice for the same slot creates each invoice once', async () => {
  await buildInvoices(context());
  await buildInvoices(context({ attempt: 2, reason: 'takeover' }));
  assert.equal(await countInvoices(), 3);
});

test('stops when the signal aborts', async () => {
  const controller = new AbortController();
  const run = buildInvoices(context({ signal: controller.signal }));
  controller.abort();
  await assert.rejects(run, { name: 'AbortError' });
});
```

</TabItem>
<TabItem label=".NET">

```csharp
// The job: a thin handler around a method that takes what it needs
public sealed class InvoiceJobs(Invoices invoices)
{
    [Cron("0 6 1 * *", Name = "monthly-invoices")]
    public Task BuildAsync(JobContext ctx) => invoices.BuildAsync(ctx.ScheduledAt, ctx.CancellationToken);
}

// The tests (xUnit)
public sealed class InvoiceTests
{
    private static readonly DateTimeOffset Slot = new(2026, 10, 1, 6, 0, 0, TimeSpan.Zero);

    [Fact]
    public async Task running_twice_for_the_same_slot_creates_each_invoice_once()
    {
        var invoices = new Invoices(TestDatabase.Create());
        await invoices.BuildAsync(Slot, CancellationToken.None);
        await invoices.BuildAsync(Slot, CancellationToken.None); // attempt 2, after a takeover
        Assert.Equal(3, await invoices.CountAsync());
    }

    [Fact]
    public async Task stops_when_the_token_is_cancelled()
    {
        using var cancelled = new CancellationTokenSource();
        await cancelled.CancelAsync();
        await Assert.ThrowsAnyAsync<OperationCanceledException>(() => new Invoices(TestDatabase.Create()).BuildAsync(Slot, cancelled.Token));
    }
}
```

</TabItem>
</Tabs>

Those two tests cover the two things a handler owes the scheduler: being safe to run twice, and stopping when asked.

## Testing with a real scheduler

To test the wiring, use `SqliteBackend` on a temporary file. It needs no server and behaves like the production lease backends.

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
import { mkdtempSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { Scheduler, SqliteBackend } from 'anarchon';

function testScheduler(instanceId = 'test') {
  const file = join(mkdtempSync(join(tmpdir(), 'cron-test-')), 'jobs.db');
  return new Scheduler({
    backend: new SqliteBackend({ database: file }),
    instanceId,
    unrefTimers: true, // don't keep the test process alive
  });
}
```

</TabItem>
<TabItem label=".NET">

```csharp
using Anarchon;
using Anarchon.Sqlite;

static string TestFile() => Path.Combine(Directory.CreateTempSubdirectory("cron-test-").FullName, "jobs.db");

static Scheduler TestScheduler(string instanceId = "test", string? file = null) => new(new SchedulerOptions
{
    Backend = new SqliteBackend($"Data Source={file ?? TestFile()}"),
    InstanceId = instanceId,
});
```

</TabItem>
</Tabs>

### Run a job without waiting for its schedule

`runNow()` (`RunNowAsync()`) executes the job at once and returns its record:

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
test('the sync job succeeds', async () => {
  const scheduler = testScheduler();
  scheduler.every('sync', '1h', syncCustomers, { catchUpMs: 0 });
  await scheduler.start();
  try {
    const run = await scheduler.runNow('sync');
    assert.equal(run.status, 'success');
  } finally {
    await scheduler.stop();
  }
});
```

</TabItem>
<TabItem label=".NET">

```csharp
[Fact]
public async Task the_sync_job_succeeds()
{
    await using var scheduler = TestScheduler(); // stopped at the end of the test
    scheduler.Every("sync", TimeSpan.FromHours(1), SyncCustomersAsync, new() { CatchUp = TimeSpan.Zero });
    await scheduler.StartAsync();

    var run = await scheduler.RunNowAsync("sync");

    Assert.Equal(RunStatus.Success, run.Status);
}
```

</TabItem>
</Tabs>

`catchUpMs: 0` (`CatchUp = TimeSpan.Zero`) stops the scheduler from also running the latest slot on start, which would otherwise add a run you didn't ask for.

### Two instances

To see that a run happens once, share the file between two schedulers:

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
test('two instances, one run per slot', async () => {
  const file = join(mkdtempSync(join(tmpdir(), 'cron-test-')), 'jobs.db');
  const ran: string[] = [];
  const instances = ['A', 'B'].map(
    (instanceId) => new Scheduler({ backend: new SqliteBackend({ database: file }), instanceId, unrefTimers: true }),
  );
  for (const scheduler of instances) {
    scheduler.every('tick', '1s', (ctx) => void ran.push(`${ctx.slot}`), { catchUpMs: 0 });
  }
  await Promise.all(instances.map((s) => s.start()));
  await new Promise((resolve) => setTimeout(resolve, 3_500));
  await Promise.all(instances.map((s) => s.stop()));

  assert.equal(new Set(ran).size, ran.length, 'no slot ran twice');
});
```

</TabItem>
<TabItem label=".NET">

```csharp
[Fact]
public async Task two_instances_one_run_per_slot()
{
    var file = TestFile();
    var ran = new ConcurrentQueue<long>();
    var instances = new[] { "A", "B" }.Select(id => TestScheduler(id, file)).ToList();
    foreach (var scheduler in instances)
    {
        scheduler.Every("tick", TimeSpan.FromSeconds(1), ctx =>
        {
            ran.Enqueue(ctx.Slot);
            return Task.CompletedTask;
        }, new() { CatchUp = TimeSpan.Zero });
    }

    await Task.WhenAll(instances.Select(s => s.StartAsync()));
    await Task.Delay(3_500);
    await Task.WhenAll(instances.Select(s => s.StopAsync()));

    Assert.Equal(ran.Count, ran.Distinct().Count()); // no slot ran twice
}
```

</TabItem>
</Tabs>

### Validation is checked at registration

Bad options throw when the job is added, so they are easy to test without starting anything:

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts
test('refuses a jitter longer than half the interval', () => {
  const scheduler = testScheduler();
  assert.throws(() => scheduler.every('bad', '2s', () => {}, { jitterMs: 1_500 }), RangeError);
});
```

</TabItem>
<TabItem label=".NET">

```csharp
[Fact]
public async Task refuses_a_jitter_longer_than_half_the_interval()
{
    await using var scheduler = TestScheduler();
    Assert.Throws<ArgumentOutOfRangeException>(() =>
        scheduler.Every("bad", TimeSpan.FromSeconds(2), _ => Task.CompletedTask, new() { Jitter = TimeSpan.FromMilliseconds(1_500) }));
}
```

</TabItem>
</Tabs>

## Don't mock the clock around a real backend

Fake timers move your process's clock, but the store keeps its own. On a lease backend the lease end is the store's time, so advancing a fake clock by an hour doesn't expire a lease, and the test ends up exercising something that can't happen. Test handlers with a fake context, and test wiring with `runNow()` and short real intervals. In .NET this holds for `SchedulerOptions.TimeProvider` too: a `FakeTimeProvider` moves the scheduler's timers, not the store's clock.

## Debugging a run

The repository ships examples made for a debugger. From a checkout:

<Tabs syncKey="language">
<TabItem label="Node.js">

```sh
pnpm install
npx tsx examples/walkthrough.ts
```

</TabItem>
<TabItem label=".NET">

```sh
git clone https://github.com/aristoteliss/anarchon-dotnet && cd anarchon-dotnet
dotnet run --project examples/Walkthrough
```

</TabItem>
</Tabs>

`examples/walkthrough.ts` (`examples/Walkthrough` in .NET) runs two instances in one process against a SQLite file, with a 10-minute lease and lateness limit, so sitting on a breakpoint doesn't change the outcome. Its header lists the functions a run passes through, in order.

In VS Code, open **Run and Debug**, choose **Example: walkthrough (step through one run)** and press F5. It pauses just before `start()`. Step in with F11, or set breakpoints on the functions below. The .NET repository has the same launch entry (**Example: Walkthrough**), which stops on `Debugger.Break()`; its header lists the C# methods, such as `JobTimers.Arm()`, `LeaseRunner.RunAsync()` and `Executor.ExecuteAsync()`.

| File under `src/scheduler/` | Function | What happens there |
| --- | --- | --- |
| `timers.ts` | `arm()` | The next slot is computed and a timer is set |
| `scheduler.ts` | `fire()` | The timer fired: the run is due |
| `lease-runner.ts` | `run()` | The claim is sent and its outcome handled |
| `lease-runner.ts` | `executeLeased()` | The heartbeat starts |
| `executor.ts` | `execute()` | Your handler is called, and the result stored |
| `lease-runner.ts` | `watch()` | A backup schedules its next check |

:::caution
A paused debugger stops your process's clock but not the store's. With normal lease timings, pausing on a breakpoint for longer than `leaseMs` (`Lease`) makes a backup take the run over. That is the library working; raise it while you debug.
:::

## Seeing what an instance does

Turn on the built-in log while you investigate:

<Tabs syncKey="language">
<TabItem label="Node.js">

```ts

```

</TabItem>
<TabItem label=".NET">

```csharp
// The scheduler logs to the "Anarchon.Scheduler" category of its LoggerFactory; a host passes its own.
```

## Common surprises

| What you see | Why |
| --- | --- |
| A run starts right after `start()` with reason `catch-up` | The latest slot was due recently and nobody ran it. Set `catchUpMs: 0` (`CatchUp = TimeSpan.Zero`) to turn that off |
| Every instance but one logs `skipped (taken)` | That is normal: one winner per run |
| `skipped (overlap)` | The previous run of that job is still going |
| A run shows twice in history | One record per attempt: it was taken over |
| A job runs on the same instance every time | `jitterMs` is 0, or that instance's clock is ahead |
| `lost` events | The instance couldn't renew its lease in time: it was paused, blocked or cut off from the store |
